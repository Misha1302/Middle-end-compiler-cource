# Занятие 10. DCE, UCE и порядок очистки

> Мёртвая инструкция и недостижимый блок — разные причины удаления

[← Карта курса](../course-map.md) · [Предыдущее занятие](../modules/09-constants.md) · [Следующее занятие](../modules/11-inlining.md)

## Результат занятия

Ты удаляешь только безопасные инструкции и поддерживаешь CFG/φ после UCE.

**Перед началом:** propagation, reachability, def-use и контракт эффектов.

## Зачем это вообще нужно

Неиспользуемый результат ещё не означает, что инструкцию можно удалить: вызов или store может иметь эффект. Недостижимый блок можно удалить целиком, потому что путь невозможен.

## Термины до заданий

| Термин | Простое объяснение | Точная опора |
|---|---|---|
| **DCE** | dead code elimination | удаляет ненужные инструкции без необходимых эффектов |
| **UCE** | unreachable code elimination | удаляет блоки, не достижимые от entry |
| **живой root** | операция, результат или эффект которой должен сохраниться | return, observable store/call и другие корни mark phase |
| **наблюдаемый эффект** | изменение поведения, видимое программе/среде | I/O, memory write, volatile/atomic, trap и т.п. |
| **φ cleanup** | исправление φ после изменения predecessors | удаление входов и упрощение одно-входовых φ |

Сначала прочитай готовые объяснения. Затем закрой таблицу и сформулируй каждый термин своими словами. Пустая формулировка ученика — это проверка после обучения, а не замена обучения.

## Первая модель

`propagation → branch simplification → UCE → pred/φ repair → folding/copy propagation → DCE`

## Разобранный пример: состояние за состоянием

```text
x1 = 4
y1 = x1 + 1       ; unused, pure
call log(x1)      ; observable
branch true, B1, B2
B2: z1 = unknown_call(); goto B3
```

`y1` удаляется DCE. `log` остаётся. `B2` удаляется UCE целиком после доказанного branch, даже если `unknown_call` имел бы эффект: путь к нему невозможен.

## Формальное правило

DCE: начать с roots и пройти назад по operands, остальные pure defs удалить. UCE: обход от entry, удалить непосещённые блоки, затем восстановить pred/succ и φ-контракт.

## Типичные ошибки

- Удалять unknown call из-за unused result.
- Запускать DCE вместо UCE на недостижимом блоке.
- Забывать обновить φ после удаления predecessor.
- Считать обычный load всегда чистым и безопасным: возможны volatile, trap и memory semantics.

## Задача A — по образцу

Классифицируй `add`, `division`, `load`, `volatile load`, `store`, `pure call`, `readonly call`, `unknown call` по условиям удаления.

<details>
<summary>Проверка задачи A — открывать после попытки</summary>

`add` удалим при unused result. Division — только если удаление не убирает наблюдаемый trap. Обычный load требует memory/trap contract; volatile load нельзя. Store нельзя без доказательства ненаблюдаемости. Pure call можно при отсутствии исключений; readonly всё ещё читает память и не автоматически pure; unknown call сохраняется.

</details>

## Задача B — перенос на новый пример

Для примера занятия 9 покажи IR после каждого шага очистки, а не только финал.

<details>
<summary>Проверка задачи B — открывать после попытки</summary>

Сначала branch становится `goto B1`; UCE удаляет B2; у φ удаляется вход B2; одно-входовая φ заменяется x1; затем `5+2→7`; DCE удаляет ставшие ненужными копии.

</details>

## Проверка на выходе

**Чем dead отличается от unreachable?**  


**Почему unknown call остаётся?**  


**Что чинить после UCE?**  


<details>
<summary>Короткие ответы</summary>

**Чем dead отличается от unreachable?**  
Dead-инструкция может находиться на достижимом пути, но не нужна; unreachable-блок вообще не выполняется.

**Почему unknown call остаётся?**  
Он может иметь наблюдаемый эффект или исключение.

**Что чинить после UCE?**  
pred/succ, φ-входы, dominance и зависимые анализы.

</details>

## Профессиональная граница

Aggressive DCE использует control dependence/postdominance и может удалять управляющие конструкции. Здесь изучается базовая безопасная версия.
