## Результат занятия

Ты строишь SSA def-use graph и выполняешь LVN с учётом типов, семантики операций и эффектов.

**Перед началом:** корректная SSA.

## Зачем это вообще нужно

Два выражения могут иметь одинаковый текст, но разные значения из-за типов, overflow, памяти или эффектов. Нужно формально определить, когда вычисление действительно повторяется.

## Термины до заданий

| Термин | Простое объяснение | Точная опора |
|---|---|---|
| **def-use** | связь определения с каждым использованием результата | ребро от SSA-def к инструкции-use |
| **data dependence** | результат одной операции нужен другой | для pure SSA-операций следует из operand def-use |
| **value number** | идентификатор уже известного значения | одинаковые доказанно эквивалентные выражения получают один VN |
| **канонический ключ** | нормализованное описание выражения | opcode, тип, flags и VN операндов |
| **наблюдаемый эффект** | изменение, которое программа или среда может заметить | store, I/O, volatile/atomic, исключение, неизвестный call и т.п. |

Сначала прочитай готовые объяснения. Затем закрой таблицу и сформулируй каждый термин своими словами. Пустая формулировка ученика — это проверка после обучения, а не замена обучения.

## Первая модель

```text
a0 = input
b0 = input
t1 = add i32 a0, b0
t2 = add i32 b0, a0
t3 = sub i32 a0, b0
```

Для обычного целочисленного `add` без различающих flags ключи `t1` и `t2` можно канонизировать сортировкой VN операндов. Для `sub` порядок сохраняется.

## Разобранный пример: состояние за состоянием

| Инструкция | Ключ | VN | Действие |
|---|---|---|---|
| `a0=input` | fresh input A | 1 | новое |
| `b0=input` | fresh input B | 2 | новое |
| `t1=add i32 a0,b0` | `(add,i32,1,2)` | 3 | новое |
| `t2=add i32 b0,a0` | `(add,i32,1,2)` | 3 | заменить на t1 |
| `t3=sub i32 a0,b0` | `(sub,i32,1,2)` | 4 | новое |

Ключ обязан включать тип и семантические flags. `add i32` и `add i64` не одно выражение.

## Формальное правило

LVN действует внутри одного базового блока и использует только факты, действующие в этой точке. Для memory operations нужен memory version/alias contract; неизвестный call обычно инвалидирует факты о памяти.

## Типичные ошибки

- Сортировать операнды некоммутативной операции.
- Игнорировать тип, overflow или fast-math flags.
- Считать два `load p` одинаковыми через возможный store/call.
- Путать CFG-edge с data-dependence edge.

<details>
<summary>Короткие ответы</summary>

**Из чего состоит ключ VN?**  
Из операции, типа, семантических флагов и VN операндов; для памяти также нужен memory state.

**Когда можно сортировать operands?**  
Только если операция коммутативна в точной семантике IR.

**Почему SSA не решает память автоматически?**  
Scalar SSA версионирует значения-регистры, но разные loads/stores могут обращаться к одной памяти.

</details>

## Профессиональная граница

Global value numbering требует учитывать пути CFG, dominance и memory state; LVN намеренно ограничен одним блоком.
