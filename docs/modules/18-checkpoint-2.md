# Занятие 18. Комплексная работа №2

> SSA-форма цикла, индуктивные переменные, LICM и снижение стоимости операций с полным эталоном

[← Карта курса](../course-map.md) · [Предыдущее занятие](../modules/17-loop-transformations.md) · [Следующее занятие](../modules/19-mock-exam-1.md)

## Результат занятия

Ты проводишь полный разбор канонического цикла и явно доказываешь допустимость каждого преобразования. Границы тела и замыкающего блока заданы в самом IR, поэтому разбиение на базовые блоки не требует догадок.

**Перед началом:** занятия 13–17 и [контракт учебного IR](../ir-contract.md).

## Зачем это вообще нужно

Проходы по циклам зависят от корректных CFG и SSA, а также от явных допущений о памяти. Если в условии не отделить тело от замыкающего блока, ответ может заявить структуру, которой нет в исходном IR. Эта работа проверяет всю цепочку и запрещает такие молчаливые исправления.

## Термины до заданий

| Термин | Простое объяснение | Точная опора |
|---|---|---|
| **SSA-форма цикла** (*loop SSA*) | использует φ-функции для значений между итерациями | начальный вход приходит из предвходного блока, обновлённый — из замыкающего |
| **Допустимость** (*legality*) | доказывает сохранение наблюдаемого поведения | все предусловия преобразования должны быть выполнены |
| **Выгодность преобразования** (*transformation profitability*) | оценивает практическую пользу преобразования | не входит в доказательство корректности |
| **Устаревание анализа** (*analysis invalidation*) | означает, что прежний результат больше не соответствует IR | изменение CFG обычно требует пересчитать Dom, DF и сведения о циклах |
| **Итоговая проверка инвариантов** (*final verifier*) | проверяет состояние после всех преобразований | контролирует CFG, φ-входы, определения, доминирование, типы и эффекты |

Сначала прочитай объяснения. Затем закрой таблицу и перескажи термины своими словами. Это проверка понимания, а не попытка угадать определение.

## Ключевая схема

`CFG и структура цикла → Dom, idom и DF → проверка SSA → индуктивные переменные → кандидаты на вынос → доказательство допустимости → преобразования → перечень устаревших анализов → итоговая проверка`

## Пошаговый разбор

В контрольном режиме первые 120 минут работа выполняется без подсказок. После этого сравнивай не только итог, а каждый артефакт слева направо:

1. блоки и терминаторы;
2. рёбра и достижимость;
3. Dom, idom и DF;
4. φ-функции и переименование;
5. доказательства допустимости;
6. IR после каждого преобразования;
7. сохранённые и устаревшие анализы.

## Формальное правило

Каждый проход получает проверенный IR, выдаёт новую версию, перечисляет сохранённые и устаревшие анализы и проходит соответствующую проверку инвариантов. Преобразование нельзя обосновать только словами «выражение не меняется» или «будет быстрее».

## Типичные ошибки

- Использовать общий шаблон помощи внутри контрольной части.
- Придумывать отдельный замыкающий блок, если в исходном IR нет границы блока.
- Выполнить LICM до доказательства существования предвходного блока и безопасности раннего выполнения.
- Снизить стоимость выражения без проверки начального случая.
- Считать любой анализ устаревшим после любого изменения или, наоборот, не пересчитать сведения после изменения CFG.

## Задача A — по образцу

Для нормализуемого линейного IR:

```text
n = input
i = 0
s = 0
k = 4 * n + 1
goto head

head:
if i >= n goto exit

body:
t = 4 * n + 1
idx = 4 * i + 3
v = load A[idx]
s = s + v + t
goto latch

latch:
i = i + 1
goto head

exit:
print s
return
```

Построй нормализованные блоки, CFG, Dom, idom, DF, естественный цикл и SSA для `i` и `s`.

<details>
<summary>Полный эталон задачи A — открывать после попытки</summary>

### 1. Нормализованные блоки

```text
PRE:
  n = input
  i = 0
  s = 0
  k = 4*n + 1
  jump H

H:
  branch i >= n, EXIT, BODY

BODY:
  t = 4*n + 1
  idx = 4*i + 3
  v = load A[idx]
  s = s + v + t
  jump L

L:
  i = i + 1
  jump H

EXIT:
  print s
  return
```

### 2. CFG

```text
PRE → H
H → BODY
H → EXIT
BODY → L
L → H
```

| Блок | `succ` | `pred` |
|---|---|---|
| PRE | {H} | ∅ |
| H | {BODY,EXIT} | {PRE,L} |
| BODY | {L} | {H} |
| L | {H} | {BODY} |
| EXIT | ∅ | {H} |

Все блоки достижимы при подходящих значениях `n`.

### 3. Dom

| Блок | Dom |
|---|---|
| PRE | {PRE} |
| H | {PRE,H} |
| BODY | {PRE,H,BODY} |
| L | {PRE,H,BODY,L} |
| EXIT | {PRE,H,EXIT} |

### 4. Непосредственные доминаторы

```text
idom(H) = PRE
idom(BODY) = H
idom(L) = BODY
idom(EXIT) = H
```

### 5. Фронты доминирования

```text
DF(PRE) = ∅
DF(H) = {H}
DF(BODY) = {H}
DF(L) = {H}
DF(EXIT) = ∅
```

Для `H` свидетелем является предшественник `L`: `H dom L`, но `H` не строго доминирует самого себя. Аналогично `BODY dom L`, поэтому `H ∈ DF(BODY)`.

### 6. Естественный цикл

`H dom L`, поэтому `L→H` — обратное ребро. Обратный сбор по `pred` даёт:

```text
{H, BODY, L}
```

`PRE` является предвходным блоком и не входит в тело цикла. `EXIT` является блоком назначения выходного ребра `H→EXIT`.

### 7. Расстановка φ-функций

`i` определяется в `PRE` и `L`; `s` — в `PRE` и `BODY`. Поскольку соответствующие блоки определений имеют `H` во фронте доминирования, в начале `H` нужны φ-функции для обоих значений.

### 8. Переименование в SSA

```text
PRE:
  n0 = input
  i0 = 0
  s0 = 0
  k0 = 4*n0 + 1
  jump H

H:
  i1 = φ[PRE: i0, L: i2]
  s1 = φ[PRE: s0, L: s2]
  branch i1 >= n0, EXIT, BODY

BODY:
  t0 = 4*n0 + 1
  idx0 = 4*i1 + 3
  v0 = load A[idx0]
  s2 = s1 + v0 + t0
  jump L

L:
  i2 = i1 + 1
  jump H

EXIT:
  print s1
  return
```

### 9. Проверка SSA

- метки входов обеих φ-функций равны `{PRE,L}`;
- `i0` и `s0` доступны на ребре `PRE→H`;
- `i2` и `s2` доступны на ребре `L→H`; значение `s2` определено в `BODY`, который доминирует `L`;
- `i1` доминирует использование в условии и `idx0`;
- `s1` доминирует использование в `s2` и `print` на выходе.

</details>

## Самостоятельная задача

Для полученного SSA выполни и обоснуй следующие кандидаты:

1. заменить `t0` на `k0`;
2. вынести `load A[idx0]`;
3. снизить стоимость вычисления `idx0`;
4. перечислить сохранённые и устаревшие анализы после каждого изменения.

<details>
<summary>Полный эталон задачи B — открывать после попытки</summary>

### 1. Замена `t0` на `k0`

Оба значения вычисляют `4*n0+1` в семантике `i32` с обёртыванием. `k0` определено в `PRE` и доминирует `BODY`. Операция чистая и не может завершиться ошибкой. Поэтому все использования `t0` можно заменить на `k0`, а определение `t0` удалить DCE.

Это глобальное устранение общего выражения или распространение доминирующего значения, а не LVN: определения находятся в разных блоках.

### 2. Попытка вынести загрузку

`idx0` зависит от `i1` и меняется между итерациями. Следовательно, адрес загрузки не является инвариантным. Уже этого достаточно, чтобы запретить вынос. Даже при неизменном адресе дополнительно потребовались бы доказательства отсутствия совпадающих записей и безопасности раннего выполнения загрузки при нулевом числе итераций.

### 3. Снижение стоимости `idx0`

Для `i(0)=0`, `i(k+1)=i(k)+1`:

```text
idx(k) = 4*i(k) + 3
idx(0) = 3
idx(k+1) = idx(k) + 4
```

Один корректный SSA-вариант:

```text
PRE:
  n0 = input
  i0 = 0
  s0 = 0
  idx_init = 3
  k0 = 4*n0 + 1
  jump H

H:
  i1 = φ[PRE: i0, L: i2]
  s1 = φ[PRE: s0, L: s2]
  idx1 = φ[PRE: idx_init, L: idx2]
  branch i1 >= n0, EXIT, BODY

BODY:
  v0 = load A[idx1]
  s2 = s1 + v0 + k0
  jump L

L:
  i2 = i1 + 1
  idx2 = idx1 + 4
  jump H

EXIT:
  print s1
  return
```

Проверка начального случая: при первой итерации старое выражение равно `4*0+3=3`. Проверка шага: увеличение `i` на 1 увеличивает `idx` на 4. Семантика обёртывания сохраняется.

### 4. Устаревание анализов

| Изменение | CFG | Dom/idom/DF | loop info | def-use/LVN/константы/живость | SSA verifier |
|---|---:|---:|---:|---:|---:|
| заменить `t0` на `k0` | сохранён | сохранены | сохранены | пересчитать | повторить |
| удалить мёртвое определение `t0` | сохранён | сохранены | сохранены | пересчитать | повторить |
| добавить рекуррентное `idx` без новых блоков | сохранён | сохранены | сохранены | пересчитать | повторить |
| создать или перенаправить блок/ребро | изменён | пересчитать | пересчитать | пересчитать | повторить после обновления φ |

### 5. Итоговая проверка

- у каждой φ-функции входы `{PRE,L}`;
- каждое SSA-имя определяется один раз;
- обычные определения доминируют использования;
- операнды φ доступны на соответствующих рёбрах;
- загрузка остаётся в теле;
- `idx1` имеет начальное значение 3 и шаг 4;
- наблюдаемый порядок `load` и `print` не изменён.

</details>

## Проверь себя

**Почему в условии явно добавлены `body` и `latch`?**  

**Почему замена `t0` на `k0` не является LVN?**  

**Что сохраняется после изменения только выражений без изменения CFG?**

<details>
<summary>Короткие ответы</summary>

Границы исключают выдуманное разбиение блоков. LVN ограничена одним блоком, а `k0` и `t0` находятся в разных блоках; здесь нужен доминирующий глобальный факт. При неизменном CFG сохраняются рёбра, Dom, idom, DF и структура цикла, но нужно обновить def-use, значения, живость и снова проверить SSA.

</details>

## Как это устроено в промышленном компиляторе

Промышленный диспетчер проходов декларативно хранит сохранённые анализы, а канонизация цикла создаёт необходимые блоки явно. Ни verifier, ни оптимизатор не должны предполагать несуществующую границу базового блока только потому, что она удобна для объяснения.
