# Занятие 20. Финальный ремонт

> Автономная процедура с готовым банком новых мини-примеров

[← Карта курса](../course-map.md) · [Предыдущее занятие](../modules/19-mock-exam-1.md)

## Результат занятия

Ты закрываешь два первичных пробела и подтверждаешь перенос на незнакомой задаче без зависимости от преподавателя.

**Перед началом:** результаты пробного зачёта.

## Зачем это вообще нужно

Перечитывание правильного ответа создаёт узнавание, но не доказывает навык. Ремонт требует уменьшенного примера, исправленного правила и нового transfer example.

## Термины до заданий

| Термин | Простое объяснение | Точная опора |
|---|---|---|
| **repair** | целенаправленное исправление конкретной ошибки | ошибка → invariant → правило → новый пример |
| **контрпример** | случай, опровергающий неверное общее правило | одного достаточно для отказа от ложного утверждения |
| **повторная трасса** | повтор алгоритма с записью состояний | проверяет механику, а не память финального ответа |
| **retrieval** | воспроизведение без подсказки | измеряет доступность знания |
| **стоп-правило** | условие завершения ремонта | два новых примера подряд без исходной ошибки |

Сначала прочитай готовые объяснения. Затем закрой таблицу и сформулируй каждый термин своими словами. Пустая формулировка ученика — это проверка после обучения, а не замена обучения.

## Первая модель

`ошибка → первый нарушенный invariant → уменьшенный пример → новая трасса → transfer example → стоп-правило`

## Разобранный пример: состояние за состоянием

**Пример ремонта DF:**

1. Ошибка: ученик добавляет join в `DF(entry)`.
2. Нарушенный invariant: алгоритм runner должен остановиться на `idom(join)`.
3. Маленький ромб: вручную поднять runner от обеих ветвей.
4. Новый пример: ромб внутри loop.
5. Стоп: два графа подряд с правильным DF и формальным свидетелем predecessor.

## Формальное правило

За одну сессию ремонтируются максимум два пробела. Для определения нужен пример и контрпример; для алгоритма — полная трасса состояния; для transformation — legality proof и контрпуть.

## Типичные ошибки

- Ждать, что преподаватель придумает единственный новый пример.
- Решать тот же пример по памяти.
- Исправлять поздний симптом раньше раннего CFG/SSA нарушения.
- Не задавать стоп-правило.

## Задача A — по образцу

Выбери первый пробел и возьми соответствующий автономный пример:

- blocks: `if p goto L; a=1; L: return a`;
- dominance: ромб с хвостом;
- DF: ромб внутри self-loop;
- SSA: две ветви и loop-carried value;
- DCE/UCE: constant branch + effectful call;
- loop: SCC с двумя входами;
- LICM: invariant division в условном body.

Запиши ошибку, invariant, исправленное правило и полную попытку.

<details>
<summary>Проверка задачи A — открывать после попытки</summary>

Решение зависит от выбранного пробела, но должно содержать четыре явно подписанных части. Отсутствие нового примера означает, что repair не завершён.

</details>

## Задача B — перенос на новый пример

Возьми второй пример той же категории из [банка задач на перенос](../practice/transfer-bank.md) и реши без конспекта. Затем проверь стоп-правило.

<details>
<summary>Проверка задачи B — открывать после попытки</summary>

Пробел закрыт, если два новых примера подряд решены без исходной ошибки и ты можешь объяснить правило и один контрпример.

</details>

## Проверка на выходе

**Почему перечитывание не repair?**  


**Как выбрать первый пробел?**  


**Когда остановиться?**  


<details>
<summary>Короткие ответы</summary>

**Почему перечитывание не repair?**  
Оно проверяет узнавание, а не самостоятельное применение.

**Как выбрать первый пробел?**  
Найти самое раннее нарушение pipeline с наибольшим каскадом.

**Когда остановиться?**  
После двух новых успешных transfer examples и точного правила без подсказки.

</details>

## Профессиональная граница

После ремонта поддерживай навык коротким spaced retrieval: через 1, 3 и 7 дней, но не повторяй уже устойчивые темы без причины.
