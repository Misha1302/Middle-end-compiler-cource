# Занятие 12. Комплексная работа №1

> От линейного IR до SSA и ациклических оптимизаций без скрытых шагов

[← Карта курса](../course-map.md) · [Предыдущее занятие](../modules/11-inlining.md) · [Следующее занятие](../modules/13-loop-concepts.md)

## Результат занятия

Ты проходишь полный pipeline и сохраняешь промежуточные артефакты, чтобы ранняя ошибка была локализуема.

**Перед началом:** занятия 1–11.

## Зачем это вообще нужно

В комплексной задаче одна ранняя ошибка каскадно портит SSA и оптимизации. Поэтому решение разбивается на проверяемые артефакты.

## Термины до заданий

| Термин | Простое объяснение | Точная опора |
|---|---|---|
| **артефакт** | проверяемый промежуточный результат | blocks, CFG, Dom, SSA или версия IR после pass |
| **инвариант** | условие корректности состояния | например, один terminator на block или один def на SSA name |
| **verifier** | механическая проверка инвариантов | останавливает pipeline на первом некорректном состоянии |
| **pass order** | порядок преобразований | выход одного прохода является входом следующего |
| **первичная ошибка** | самый ранний нарушенный инвариант | её исправление обычно устраняет каскад вторичных симптомов |

Сначала прочитай готовые объяснения. Затем закрой таблицу и сформулируй каждый термин своими словами. Пустая формулировка ученика — это проверка после обучения, а не замена обучения.

## Первая модель

`linear IR → blocks → CFG/reachability → Dom/idom/DF → φ → renaming/verifier → propagation → UCE/φ repair → LVN/DCE`

## Разобранный пример: состояние за состоянием

Для каждого перехода сохраняй отдельную версию. Если verifier SSA падает, не продолжай DCE на заведомо некорректном IR; исправь первый нарушенный контракт.

## Формальное правило

Комплексное решение засчитывается не только по финалу. Для каждого этапа должны быть вход, выход, invariant check и явное решение об инвалидированных анализах.

## Типичные ошибки

- Прыгать сразу к очевидной оптимизации.
- Молча исправлять исходный граф и не показывать допущение.
- Переносить ошибочный Dom в SSA.
- Показывать только финальный IR.

## Задача A — по образцу

Для IR ниже построй blocks, CFG, reachability, Dom/idom/DF и SSA:

```text
p=input
x=0
if p goto L1
x=4
goto L2
L1: x=7
L2: y=x+1
print y
```

<details>
<summary>Проверка задачи A — открывать после попытки</summary>

Блоки образуют ромб. В join L2 нужна φ для `x`: `x3=φ(false:x1,true:x2)`, затем `y1=x3+1`. `idom(join)=entry`, DF обеих ветвей содержит join.

</details>

## Задача B — перенос на новый пример

Продолжи pipeline для случаев `p=true` и `p` неизвестно; покажи, где допустимы UCE, φ cleanup и folding.

<details>
<summary>Проверка задачи B — открывать после попытки</summary>

При `p=true` ложная ветвь удаляется, φ упрощается до 7, `y=8`. При неизвестном p обе ветви остаются, φ не константа; можно удалить только независимо мёртвые pure defs.

</details>

**Почему нужен отдельный verifier после SSA?**  


**Какая ошибка считается первичной?**  


**Когда анализ нужно пересчитать?**  


<details>
<summary>Короткие ответы</summary>

**Почему нужен отдельный verifier после SSA?**  
Чтобы не запускать оптимизации на IR с повторными defs, неверными φ или dominance violations.

**Какая ошибка считается первичной?**  
Самое раннее нарушение контракта, из которого следуют последующие неверные результаты.

**Когда анализ нужно пересчитать?**  
Когда преобразование изменило данные, от которых этот анализ зависит, например CFG или defs.

</details>
