# Занятие 12. Комплексная работа №1

> От линейного IR до SSA и ациклических оптимизаций с полным эталоном промежуточных состояний

[← Карта курса](../course-map.md) · [Предыдущее занятие](../modules/11-inlining.md) · [Следующее занятие](../modules/13-loop-concepts.md)

## Результат занятия

Ты проходишь всю цепочку анализа, сохраняешь промежуточные результаты и находишь первую ошибку по полному эталону, а не по нескольким финальным ориентирам.

**Перед началом:** занятия 1–11 и [контракт учебного IR](../ir-contract.md).

## Зачем это вообще нужно

В комплексной задаче одна ранняя ошибка каскадно портит SSA и оптимизации. Поэтому решение разбивается на проверяемые артефакты: нормализованные блоки, CFG, таблицы Dom, дерево доминаторов, DF, SSA и версии IR после проходов.

## Термины до заданий

| Термин | Простое объяснение | Точная опора |
|---|---|---|
| **Артефакт** | проверяемый промежуточный результат | список блоков, CFG, множества Dom, SSA или версия IR после прохода |
| **Инвариант** | условие корректности состояния | например, один терминатор на нормализованный блок или одно определение SSA-имени |
| **Проверка инвариантов** (*verifier*) | механически или вручную проверяет контракт представления | останавливает цепочку на первом некорректном состоянии |
| **Порядок проходов** (*pass order*) | задаёт последовательность анализов и преобразований | выход одного прохода становится входом следующего |
| **Первичная ошибка** | самое раннее нарушение инварианта | её исправление обычно устраняет поздние производные симптомы |

Сначала прочитай объяснения. Затем закрой таблицу и перескажи термины своими словами. Это проверка понимания, а не попытка угадать определение.

## Ключевая схема

`линейный IR → лидеры и блоки → нормализация терминаторов → CFG и достижимость → Dom, idom и DF → φ-функции → переименование и проверка SSA → распространение констант → UCE и обновление φ-функций → LVN и DCE`

## Пошаговый разбор

Для каждого перехода сохраняй отдельную версию. Если проверка SSA не проходит, не продолжай DCE на заведомо некорректном IR. Сначала исправь самое раннее нарушение.

Минимальный журнал:

| Этап | Вход | Выход | Проверка | Что устарело |
|---|---|---|---|---|
| блоки | линейный IR | нормализованные блоки | один терминатор на блок | — |
| CFG | блоки | `pred/succ`, достижимость | симметрия рёбер | — |
| Dom/DF | CFG | Dom, idom, DF | определения через пути | — |
| SSA | CFG и DF | SSA-IR | определения, φ-входы, доминирование | def-use |
| изменение CFG | SSA-IR | новый CFG | `pred/succ`, φ, достижимость | Dom, idom, DF, loop info |
| изменение выражений | SSA-IR | новый SSA-IR | типы, эффекты, использования | def-use, LVN, константы, живость |

## Формальное правило

Комплексное решение оценивается не только по конечному результату. Для каждого этапа должны быть:

1. точный вход;
2. полный выход;
3. проверка инвариантов;
4. список сохранённых и устаревших анализов;
5. первая точка расхождения с эталоном, если ответ неверен.

## Типичные ошибки

- Прыгать сразу к очевидной оптимизации.
- Молча добавлять отсутствующий переход или `return` и не показывать допущение.
- Строить SSA на ошибочно вычисленных множествах Dom.
- Показывать только итоговый IR.
- Считать короткий список ориентиров полноценным эталоном комплексной задачи.

## Задача A — по образцу

Для IR ниже построй базовые блоки, нормализованный CFG, достижимость, Dom, idom, DF и SSA:

```text
p = input
x = 0
if p goto L1
x = 4
goto L2
L1:
x = 7
L2:
y = x + 1
print y
return
```

<details>
<summary>Полный эталон задачи A — открывать после попытки</summary>

### 1. Лидеры и нормализованные блоки

Лидеры: первая инструкция, инструкция `x=4` после условного перехода, цели `L1` и `L2`.

```text
B0:
  p = input
  x = 0
  branch p, B2, B1

B1:
  x = 4
  jump B3

B2:
  x = 7
  jump B3

B3:
  y = x + 1
  print y
  return
```

### 2. CFG и достижимость

Рёбра:

```text
B0 → B1
B0 → B2
B1 → B3
B2 → B3
```

| Блок | `succ` | `pred` |
|---|---|---|
| B0 | {B1,B2} | ∅ |
| B1 | {B3} | {B0} |
| B2 | {B3} | {B0} |
| B3 | ∅ | {B1,B2} |

Все четыре блока достижимы из `B0`.

### 3. Множества доминаторов

| Блок | Dom |
|---|---|
| B0 | {B0} |
| B1 | {B0,B1} |
| B2 | {B0,B2} |
| B3 | {B0,B3} |

### 4. Непосредственные доминаторы

```text
idom(B1) = B0
idom(B2) = B0
idom(B3) = B0
```

Дерево доминаторов: у `B0` три ребёнка — `B1`, `B2`, `B3`.

### 5. Фронты доминирования

```text
DF(B0) = ∅
DF(B1) = {B3}
DF(B2) = {B3}
DF(B3) = ∅
```

`B3` входит во фронты обеих ветвей, потому что каждая ветвь доминирует своего предшественника `B3`, но не строго доминирует сам `B3`.

### 6. Расстановка φ-функций

`x` определяется в `B0`, `B1` и `B2`. Из-за определений в `B1` и `B2` в начале `B3` нужна одна φ-функция.

### 7. Переименование в SSA

```text
B0:
  p0 = input
  x0 = 0
  branch p0, B2, B1

B1:
  x1 = 4
  jump B3

B2:
  x2 = 7
  jump B3

B3:
  x3 = φ[B1: x1, B2: x2]
  y0 = x3 + 1
  print y0
  return
```

### 8. Проверка SSA

- каждое имя `p0`, `x0`, `x1`, `x2`, `x3`, `y0` определяется один раз;
- метки входов φ-функции `{B1,B2}` совпадают с `pred(B3)`;
- `x1` доступен на ребре `B1→B3`, `x2` — на `B2→B3`;
- `x3` доминирует использование в `y0`;
- `x0` после построения SSA не имеет использований и может быть удалён DCE.

</details>

## Самостоятельная задача

Продолжи цепочку отдельно для трёх случаев:

1. `p=true`;
2. `p=false`;
3. `p` неизвестно.

Покажи условный переход, UCE, обновление φ-функции, свёртку и DCE после каждого изменения.

<details>
<summary>Полный эталон задачи B — открывать после попытки</summary>

### Случай `p=true`

1. `branch p0, B2, B1` заменяется на `jump B2`.
2. `B1` становится недостижимым и удаляется.
3. `pred(B3)={B2}`; вход `[B1:x1]` удаляется.
4. `x3 = φ[B2:x2]` заменяется копией `x3=x2`, затем распространяется `x2=7`.
5. `y0=7+1` сворачивается в `y0=8`.
6. DCE удаляет `x0`, копию `x3` и другие неиспользуемые чистые определения.

Итоговый наблюдаемый результат: `print 8`.

### Случай `p=false`

1. Переход заменяется на `jump B1`.
2. `B2` удаляется UCE.
3. φ-функция получает единственный вход `B1:x1` и упрощается.
4. `x1=4`, поэтому `y0=5`.

Итоговый наблюдаемый результат: `print 5`.

### Случай `p` неизвестно

Обе ветви достижимы. φ-функция не является константой, потому что её возможные значения равны 4 и 7. Можно удалить `x0=0`, так как обе ветви переопределяют `x` до использования, но нельзя удалять ни одну ветвь или заменять `x3` одной константой.

### Устаревание анализов

Удаление блока или ребра делает недействительными достижимость, `pred/succ`, Dom, idom, DF и проверку φ-входов. Замена выражений без изменения CFG сохраняет структуру графа, но требует обновить def-use, факты констант и живость.

</details>

## Проверь себя

**Почему после построения SSA нужна отдельная проверка инвариантов?**  

**Какая ошибка считается первичной?**  

**Почему `x=0` можно удалить даже при неизвестном `p`?**

<details>
<summary>Короткие ответы</summary>

SSA нужно проверить до оптимизаций, чтобы не продолжать работу с повторными определениями, неверными φ-входами или нарушением доминирования. Первичная ошибка — самое раннее состояние, нарушившее контракт. Начальное `x=0` не достигает использования: на каждом пути к `B3` значение `x` переопределяется в `B1` или `B2`.

</details>

## Как это устроено в промышленном компиляторе

Диспетчер проходов хранит сведения о сохранённых и устаревших анализах, а verifier запускается после рискованных преобразований. Полный эталон нужен не для запоминания ответа, а для поиска первого состояния, где собственная трасса разошлась с корректной.
