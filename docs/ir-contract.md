# Контракт учебного IR v1

Все обязательные задачи используют этот контракт, если условие явно не задаёт отличия. Цель контракта — сделать ответы однозначными: оптимизацию нельзя разрешать или запрещать на основании неявной семантики.

## Две формы записи управления

В курсе встречаются две формы одного и того же управления.

### Линейный IR

В линейной записи метки и инструкции расположены последовательно. Если блок заканчивается перед следующей меткой без `goto`, управление неявно переходит к следующему расположенному блоку. Такой переход называется `fall-through`.

### Нормализованный CFG-IR

После построения базовых блоков каждый неявный переход заменяется явным `goto`. В нормализованном CFG-IR каждый достижимый базовый блок заканчивается ровно одним терминатором:

```text
jump target
branch condition, when_true, when_false
return value
return
unreachable
```

Все анализы и преобразования курса работают с нормализованным CFG-IR. Поэтому фраза «каждый блок имеет терминатор» относится именно к этой форме.

## CFG

- терминатор перечисляет все непосредственные блоки-последователи;
- `v ∈ succ(u)` тогда и только тогда, когда `u ∈ pred(v)`;
- анализы по умолчанию работают только с вершинами, достижимыми из входного блока;
- порядок блоков в файле после нормализации не создаёт дополнительных рёбер;
- блок с `return` или `unreachable` не имеет обычных последователей.

## Типы и арифметика

В обязательных задачах используются типы `i1` и `i32`, если не указано иное.

- `i1` содержит значения `false` и `true`;
- `i32` — целое число фиксированной ширины;
- `add`, `sub` и `mul` для `i32` выполняются с обёртыванием по модулю `2^32`;
- сравнения `eq`, `ne`, `slt`, `sle`, `sgt`, `sge` не имеют побочных эффектов и возвращают `i1`;
- `sdiv i32` выдаёт наблюдаемую ошибку при делении на ноль и при `INT_MIN / -1`;
- вычисления с плавающей точкой не входят в обязательные задачи, пока условие явно не задаст тип, NaN, бесконечности и разрешённые упрощения.

Математическое тождество разрешает преобразование только тогда, когда оно верно для этой точной семантики операций.

## SSA

- каждое SSA-имя имеет ровно одно определение;
- обычное определение доминирует каждое обычное использование;
- φ-функции расположены в начале блока;
- используется единая запись `x3 = φ[B1: x1, B2: x2]`;
- φ-функция имеет ровно один вход для каждого достижимого предшественника блока;
- использование операнда φ-функции считается расположенным на соответствующем входящем ребре;
- результат φ-функции определяется в начале самого блока.

Недостижимые блоки сначала удаляются или явно исключаются из рассматриваемого CFG. После этого набор меток входов φ-функции должен точно совпадать с `pred` блока.

## Память

Обычная SSA версионирует вычисленные значения, но не состояние памяти.

- `load address` читает память и может завершиться наблюдаемой ошибкой при недопустимом адресе;
- две загрузки из текстуально одинакового адреса не считаются равными, если между ними возможна совпадающая запись;
- `store address, value` изменяет память и является наблюдаемым эффектом;
- `volatile load` и `volatile store` всегда являются наблюдаемыми операциями;
- разные адресные выражения могут обозначать одну область памяти, пока анализ псевдонимов не доказал обратное;
- отсутствие факта о памяти трактуется консервативно, а не как разрешение оптимизации.

## Вызовы, ввод-вывод и ошибки

В условии задачи вызов получает один из следующих контрактов.

| Контракт | Читает память | Изменяет память | Может завершиться ошибкой | Можно удалить неиспользуемый результат |
|---|---:|---:|---:|---:|
| `pure` | нет | нет | нет | да |
| `readonly` | да | нет | да | только если отдельно доказано отсутствие ошибки и чтение не является наблюдаемым |
| `writeonly` | нет | да | да | нет без доказательства ненаблюдаемости записи |
| `unknown` | возможно | возможно | возможно | нет |

- `input` и `print` являются наблюдаемыми операциями;
- `print` нельзя переставлять относительно другого наблюдаемого эффекта без доказательства эквивалентности;
- инструкция, способная завершиться наблюдаемой ошибкой, не считается безопасной для удаления или раннего выполнения только потому, что её результат не используется.

Если контракт вызова не указан, используется `unknown`.

## Изменение IR и устаревание анализов

После изменения рёбер или блоков CFG прежними нельзя считать:

- достижимость;
- `pred` и `succ`;
- Dom, `idom` и DF;
- сведения о циклах;
- входы φ-функций и доказательства доминирования использований.

После изменения определений или операндов без изменения CFG обычно устаревают:

- связи определений и использований;
- номера значений;
- распространённые константы;
- живость и результаты DCE.

Преобразование обязано либо пересчитать анализ, либо явно доказать, что его результат сохранён.

## Допустимость и выгодность

**Допустимость** доказывает, что преобразование сохраняет наблюдаемое поведение программы в рамках этого контракта. **Выгодность** оценивает размер кода, время выполнения, время компиляции, локальность и давление на регистры. Оценка выгоды никогда не заменяет доказательство допустимости.
